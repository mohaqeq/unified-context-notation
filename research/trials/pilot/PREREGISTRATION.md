# Pilot pre-registration (written and committed before any pilot run)

## Question

Does giving a coding agent a **UCN projection with the validator in its loop (B)** do better than the project's real
**lightweight stack: AGENTS.md with import-linter in its loop (L)**, and better than **no agent docs (C)**, when it
implements realistic changes in an existing codebase?

## Setup

- **Repository:** sqlfluff at commit `1682e11` (269 package files; architecture rules documented in AGENTS.md and enforced by
  import-linter contracts). The UCN model is `trials/sqlfluff/model.deny.ucn`.
- **Tasks:** 12, written by a **different model (Claude Sonnet) that never sees the UCN model or these tools**.
  - 9 *tempting* tasks: the most direct implementation would break a documented rule.
  - 3 *control* tasks: ordinary changes with no particular temptation.
- **Graders:** each task has a hidden behavioral grader that the author must show **fails on unchanged code** and **passes
  on the author's reference solution**. The reference solution must keep all 4 import-linter contracts.
- **Agents:** Claude Haiku. Per task: C × 1, L × 2, B × 2, so 60 runs. The B projection is generated by
  `tools/ucn_project.py` (budget 2500 tokens) from the task text alone.
- **Grading** (`tools/recon.py grade`, everything in containers):
  - **success** = all hidden grader tests pass;
  - **violation** = the project's own import-linter contracts break, or the UCN validator reports a new architecture or
    convention violation;
  - **tampering** = an edit to model.ucn, context.ucn or the import-linter contracts.

## Hypotheses and decision rules (fixed now)

| # | Hypothesis | Decision rule |
|---|---|---|
| H1 | B's success rate is **not worse** than L's | B − L ≥ −10 percentage points (point estimate); reported with an exact McNemar test on the paired runs |
| H2 | B's violation rate on tempting tasks is **not higher** than L's | B ≤ L |
| H3 | B uses **fewer tokens** than L | median tokens B < L |
| H4 | Both checked arms beat **no docs** on violations | B < C and L < C on tempting tasks |

- **Outcome for UCN:**
  - *Supported* if H1, H2 and H3 hold.
  - *Not supported* if H1 fails (UCN costs task success) or H2 fails (UCN lets more violations through).
  - *Inconclusive* otherwise.
- **Statistics:** with 24 paired runs (12 tasks × 2) and clustered runs per task, this pilot cannot detect small effects. A
  significant difference is not expected; the pilot is meant to catch *large* harm or benefit and to test the method.
- **`tools/pilot_eval.py`** is also run on `pilot.json` for its GO / KILL / EXTEND output. Its upkeep criterion has no
  minutes data here. Model upkeep was measured separately as model edits per commit (0 in 600 sqlfluff commits under the
  deny-list policy, [docs/07 §7.6](../../docs/07-trial-results.md)), so its decision is expected to be EXTEND for lack of
  upkeep minutes.

## What would change the conclusion

- Any tampering in B (editing the model to get green) counts as a violation and is reported separately.
- A task whose grader turns out to be wrong (fails on a correct implementation) is excluded from success for all arms,
  and the exclusion is reported.
