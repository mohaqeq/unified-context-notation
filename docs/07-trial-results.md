# 7. Trials on Real Repositories (v0.4–v0.5.1)

After implementing the first four items of the v0.4 plan ([06 §6.5](06-review-synthesis-v0.3.md#65-what-v04-should-do-consolidated-plan)), UCN was driven against three open-source repositories, to see whether it brings value. Everything here was done with UCN's own tools, which only **read** files. Running third-party code (the repositories' test suites, import-linter from PyPI) was blocked in this environment, and that limits some comparisons below.

| Repository | Language, size | What it tested | Artifacts |
|---|---|---|---|
| [sqlfluff/sqlfluff](https://github.com/sqlfluff/sqlfluff) @ `1682e11` | Python, 269 package files | The full reverse → adopt → forward workflow on a project that **already has the lightweight stack** (`AGENTS.md` files and import-linter contracts in CI); upkeep over 5.5 months of history | [trials/sqlfluff/](../trials/sqlfluff/) |
| [excalidraw/excalidraw](https://github.com/excalidraw/excalidraw) @ `701b901` | TypeScript monorepo, 723 files, tsconfig path aliases | Import resolution in a modern TS monorepo; the declared architecture (workspace `package.json` dependencies) against the code | [trials/excalidraw/](../trials/excalidraw/) |
| [cosmicpython/code](https://github.com/cosmicpython/code) @ `14c8479` | Python, 21 files, layered DDD architecture | Whether UCN changes how a coding agent behaves on tasks that tempt architecture violations | [trials/cosmicpython/](../trials/cosmicpython/) |

## 7.1 sqlfluff: a project that already has the lightweight stack

sqlfluff is the reviewers' "lightweight stack" in practice. It has five `AGENTS.md` files (7,757 words) and import-linter contracts in `pyproject.toml`, run by `tox` in CI:
- *core* must not import api/cli/dialects/rules/utils;
- *api* must not import cli;
- the helpers are independent of each other;
- inside core, the layers are linter > rules > parser > errors > types > helpers;
- 4 documented `ignore_imports` exceptions.

**Workflow, step by step:**

1. **Model from the docs** ([model.step1.ucn](../trials/sqlfluff/model.step1.ucn)): 21 components with `code:` globs, plus only the documented core layering as relations. Reverse mode.
2. **First run (1.1 s):**
   - 0 findings against any of sqlfluff's contracts, consistent with their CI;
   - **the 4 documented exceptions surfaced exactly** (errors → rules, errors → parser, plugin hookspecs → rules, formatter → linter);
   - 71 other dependencies their contracts allow but the allow-list model had not declared yet;
   - one transitive dependency through the package barrel (`cli/autocomplete.py → sqlfluff/__init__.py → api`), found by the new pass-through closure.
3. **`--propose`** turned the 71 dependencies into 15 lines of `uses`. The 4 exceptions became **deviations** with an approver and an expiry date ([model.ucn](../trials/sqlfluff/model.ucn)).
4. **Two conventions** found by inspection and encoded as deterministic checks (`only sqlfluff/{cli,utils/testing}/** imports click`, `only sqlfluff/core/templaters/** imports jinja2`). Both hold.
5. **Adopt gate:**
   - with the step-1 model: blocked, 75 blockers;
   - with the completed model: passed; `--apply` wrote `mode: forward baseline: 1682e11` and an adoption-log line;
   - forward check: 0 violations, 4 waived.

**Finding 1: a contradiction between the agent instructions and the code.**
- sqlfluff's root `AGENTS.md` says under *Lazy Loading*: "Never import dialect modules directly." **12 modules** in `rules/` and `utils/` import `sqlfluff.dialects.dialect_ansi` directly (for example `rules/aliasing/AL01.py:8`).
- Neither import-linter (no contract covers it) nor the prose catches this.
- The rule's intent is probably narrower (load dialects lazily; importing ANSI segment classes is fine). Either way, an agent reading the instructions literally is told the opposite of what the code does.
- UCN records it as `conflict LazyDialectsVsCode` with both sides, and the adopt gate for `Rules` now **blocks** until a maintainer resolves it.

**Finding 2: a method flaw.** In step 3, `--propose` accepted `Rules → Dialects` as observed reality, because the prose rule wasn't encoded. **Bootstrapping a model from code launders contradictions with prose rules**, unless stated "never" rules are encoded first. That needs a `forbids` relation (v0.4 plan item 6), so `--propose` can refuse to propose a forbidden dependency and emit a conflict candidate instead.

**Finding 3: upkeep is low.** I replayed the 600 commits between 2026-05-23 and 2026-11-05 ([history.json](../trials/sqlfluff/history.json), [replay.py](../trials/replay.py)):

| Metric | Value |
|---|---|
| Commits that changed an import line in `src/sqlfluff` | 49 |
| Commits that added a new component-level dependency (= a model update under UCN's allow-list) | **3** (`d118e55`, `9c310b7`, `f117441`), each one `uses` line, generated by `--propose` |
| Commits that removed a component-level dependency | 0 |
| Commits that violated a documented architecture rule | 0 (consistent with import-linter in CI) |
| Edits to sqlfluff's import-linter config in the same window | 0 |
| Validator time per commit | 2.4–3.1 s (fresh extraction from `git archive` each time) |

All 3 new dependencies point down into the helpers layer and are legitimate. So the allow-list's cost was 3 one-line edits in 600 commits, and its benefit here was *visibility* of 3 architecture changes, not caught defects.

**Finding 4: what UCN adds over sqlfluff's lightweight stack**, honestly:
- **Same detection** of the contracted rules.
- **Governance the stack lacks:** expiring, approved deviations instead of permanent `ignore_imports`.
- **A checked form** of rules that today exist only as prose (the dialect rule; the click and jinja2 conventions).
- **One model** that an agent can read, and that compiles to import-linter. [generated.importlinter](../trials/sqlfluff/generated.importlinter) has 24 contracts; *not run here*, because executing import-linter was blocked.
- **What it costs:** an allow-list is more verbose than their deny-list (83 relations vs ~15 forbidden entries), and every new legitimate dependency is a model edit.

**Usability findings:**
- The depth cap of 4 was too shallow (system › package › core › helpers › module); the system node had to be dropped.
- A sub-component doesn't inherit its parent's permissions, so `Ansi` had to repeat `uses CoreDialects, Parser`.

## 7.2 excalidraw: declared architecture vs code in a TypeScript monorepo

**Model** ([model.ucn](../trials/excalidraw/model.ucn)): one container per workspace package, with `uses` taken from each `package.json`'s `@excalidraw/*` dependencies, plus "the app uses the library" from `CLAUDE.md`. Imports resolve through the root `tsconfig.json` `paths` (16 aliases such as `@excalidraw/element/*`).

**Resolution quality:**
- All 327 imports that didn't resolve to code were **assets** (230 `.woff2`, 86 `.scss`, 7 `.css`, 4 `.json`). Asset imports are now classified as such.
- No alias failed to resolve.
- 8 computed dynamic imports are reported as a blind spot.

**Findings** (22 undeclared package-level dependencies, hand-checked):

| Finding | Kind | Assessment |
|---|---|---|
| `@excalidraw/common` imports `@excalidraw/math` at **runtime** (`clamp`, `degreesToRadians` in `common/src/colors.ts`), while `math` declares a dependency on `common` | circular dependency between published packages; undeclared in `common/package.json` | **true positive** |
| `@excalidraw/element` imports `@excalidraw/utils/shape` at runtime (`getCurvePathOps`), and `utils` imports `element` | circular, undeclared in `element/package.json` | **true positive** |
| `@excalidraw/element` imports `@excalidraw/laser-pointer` at runtime | undeclared in `element/package.json` | **true positive** |
| `common` → `element/types` | type-only cycle | true, low impact |
| `*/global.d.ts` → `excalidraw/global` | type declaration includes | true, benign |
| `math` → `utils`, `library` → `app` | only from test files | true, test-only |
| app → common/element/math, tooling → packages | the app and tools use packages through aliases, not `package.json` | true; the declared model was incomplete |

Whether the undeclared runtime dependencies break published packages depends on how each package is bundled; that was not verified. They are real inconsistencies between the declared architecture and the code. Existing tools would also catch the undeclared ones (for example eslint-plugin-import `no-extraneous-dependencies`, dependency-cruiser), so the value here is the **zero-configuration path**: a 30-line model derived from the manifests, checked in 1.4 s.

## 7.3 cosmicpython: does UCN change agent behavior?

**Setup** ([results.json](../trials/cosmicpython/results.json), [grade.py](../trials/cosmicpython/grade.py)):
- **Model** ([model.ucn](../trials/cosmicpython/model.ucn)): the book's architecture. The domain depends on nothing; adapters on the domain; the service layer orchestrates; the entrypoints go through the service layer and views. Plus 5 business-rule requirements and 3 library conventions (SQLAlchemy, Flask and Redis only in their layers). It matches the code: 0 violations.
- **Tasks:** 4, each tempting a violation:
  - T1, emails on deallocation (tempting: notifications in the domain);
  - T2, discontinued products with an HTTP 400 (tempting: Flask concerns in the domain);
  - T3, an `allocated_at` timestamp in the database (tempting: SQLAlchemy in the domain or views);
  - T4, a `GET /stock/<sku>` endpoint (tempting: an entrypoint querying adapters directly).
- **Conditions:**
  - **C:** no instructions;
  - **A:** an `AGENTS.md` with *the same rules* in prose ([AGENTS.md](../trials/cosmicpython/AGENTS.md)), for information parity;
  - **B:** the UCN model plus the validator in the loop, with the instruction not to edit the model.
- **Agents:** a small model (Claude Haiku), A and B twice per task, C once: 20 runs.
- **Grading:** every run checked against the **pristine** model (so edits to the model can't help), tampering detection, and a manual read of every import line the agents added.

**Results:**

| Condition | Runs | Runs with an architecture or convention violation | Model or doc tampering | Avg tokens | Avg time | Avg tool calls |
|---|---|---|---|---|---|---|
| C: no instructions | 4 | **0** | — | 56.3k | 58.0 s | 10.2 |
| A: AGENTS.md (same rules) | 8 | **0** | 0 | 59.9k (+6%) | 62.1 s | 13.1 |
| B: UCN + validator | 8 | **0** | 0 | 61.4k (+9%) | 64.0 s | 15.1 |

**Reading:**
- **No difference, because nobody violated anything, not even without instructions.** In a small, clean codebase whose structure demonstrates the architecture, the agent copied the existing patterns. The tasks were not tempting enough. Architecture guidance, in prose or as a checked model, had nothing to prevent.
- **The validator's zero was correct.** The manual audit of added imports found no layer breaches.
- **The B agents ran the validator and respected it.** None edited the model; two proposed model changes in their summaries instead (a new requirement for the discontinued rule, and a new requirement for the email), which is the intended behavior.
- **Model-influenced design, once:** T2-B2 translated the domain exception in the service layer "to keep the entrypoint dependent only on the service layer" (citing `ThroughTheServiceLayer`). The other runs imported the domain exception in the entrypoint, which the model also allows.
- **The quality problem that did occur is outside UCN's scope.** Two runs (T3-B2 with UCN, T3-C1 without) put a `datetime` into the `Allocated` event, which the Redis publisher serializes with `json.dumps(asdict(event))`: a runtime bug. One AGENTS.md run (T3-A2) noticed and avoided it. Neither format encodes this, and neither could check it statically without a rule such as "events are JSON-serializable".
- **Cost:** +6% tokens for AGENTS.md and +9% for UCN with the validator, over no instructions.

**What this does and doesn't show:**
- It shows that **UCN doesn't help where the code already teaches the architecture**, and that its overhead there is small.
- It doesn't test the case where value is expected: large or eroded codebases, and rules that can't be inferred from neighboring code (like sqlfluff's dialect rule). n is tiny, and the agent was one small model.
- The next experiment must use tasks drawn from **rules that aren't visible in the code** and a **larger, less uniform codebase**, as the reviewers' pilot design already said (information parity, external tempting tasks).

## 7.5 Conclusion: does it bring value?

**Where it clearly helped:**
1. **Finding contradictions between prose rules and code.** The sqlfluff dialect rule contradicts 12 modules, and neither the project's AGENTS.md nor its import-linter contracts noticed.
2. **Finding inconsistencies between declared and actual architecture.** excalidraw has circular, undeclared runtime dependencies between published packages.
3. **Governing exceptions.** sqlfluff's permanent `ignore_imports` become approved, expiring deviations.
4. **Doing it cheaply.** About 1 s per check on real repos, about 3 model edits per 600 commits, models of 30–110 lines, and rule edits generated by `--propose`.

**Where it did not help:**
- On a clean, small codebase, a checked model didn't change agent behavior. Neither did prose, because there was nothing to prevent.
- On a repo that already enforces its rules, UCN caught no defects that the existing stack missed, except the prose-only rule.

**What to fix next** (in priority order):
1. Add **`forbids` / `layer` / `acyclic`**, so stated "never" rules are encoded before bootstrapping, and `--propose` can't launder them.
2. Make the **depth cap** larger (or remove it) and offer **opt-in permission inheritance** for sub-components.
3. **Run the generated import-linter and dependency-cruiser configs** in an environment that allows it, and compare them with the validator on these repositories.
4. Run the **pilot** on a larger, older codebase with **rules that aren't visible in the code**, with tempting tasks written by people outside the project.

## 7.6 Second round (v0.5): rule vocabulary, deny-list policy, and agents on hidden rules

The first round produced three concrete demands:
- encode stated "never" rules before bootstrapping;
- reduce allow-list upkeep;
- test agents on rules that *aren't* visible in neighboring code.

v0.5 adds:
- `forbids`, `layers: A > B > C` (**transitive**, checked on the module graph, as in import-linter), `independent`, `acyclic`;
- `policy: deny` (undeclared dependencies are allowed; only stated rules are enforced);
- opt-in `inherit: yes`, and a depth cap of 6;
- a `CONFLICT` class for code that contradicts a stated rule where the code is authoritative;
- detection of deviations that match no dependency.

`--propose` now **refuses** to accept a forbidden dependency and drafts a `conflict` instead.

### sqlfluff, re-modelled ([model.deny.ucn](../trials/sqlfluff/model.deny.ucn))

sqlfluff's import-linter contracts are encoded one-to-one (`forbids`, `layers`, `independent`, the 4 `ignore_imports` as deviations), plus the AGENTS.md dialect rule as `forbids`.

| | Allow-list model (v0.4) | Deny-list model (v0.5) |
|---|---|---|
| Model size | 124 lines, 83 relations | 80 lines |
| Model edits needed over 600 commits | 3 | **0** ([history.deny.json](../trials/sqlfluff/history.deny.json)) |
| Dialect-rule contradiction | laundered by `--propose` until encoded by hand | caught as a violation in forward mode; `--propose` refuses and drafts a `conflict` |
| Their 4 exceptions | waived | waived, **and each is shown to be necessary** (below) |

**Agreement with import-linter's semantics on real code.** Removing each exception reproduces the exact chain that made sqlfluff add it:

| Exception removed | Chain the validator reports |
|---|---|
| errors → rules, errors → parser | direct layer violations from `core/errors.py` |
| formatter → linter | `core/rules/base.py → core/templaters/base.py → core/formatter.py → core/linter/__init__.py` |
| plugin hookspecs → rules | `core/parser/context.py → core/config/fluffconfig.py → core/plugin/host.py → core/plugin/hookspecs.py → core/rules/base.py` |

A first version searched the element graph and produced false chains through container-level files (`core/__init__.py`, `core/timing.py`). Searching the file graph fixed it.

**Generated import-linter config** ([generated.deny.importlinter](../trials/sqlfluff/generated.deny.importlinter)):
- a layers contract with the same 4 `ignore_imports` as sqlfluff's hand-written one, plus the independence and forbidden contracts;
- 4 contracts sqlfluff doesn't have (2 dialect rules, 2 library conventions).

Reviewing the generated file found three exporter bugs, all fixed:
- missing transitive ignores;
- redundant source modules;
- convention contracts whose sources included the allowed files.

The config has still not been *run* through import-linter (blocked in this environment).

### Agent experiment v2: sqlfluff, rules that aren't visible locally

**Setup** ([agent-experiment/](../trials/sqlfluff/agent-experiment/)):
- **Tasks:** 4, each tempting a violation of a non-local rule:
  - T1, logging rule codes and the ANSI root segment from the linter (core → rules or dialects);
  - T2, a segment-describing helper in the lowest layer (helpers → parser);
  - T3, colored CLI-style output from the public API (api → cli);
  - T4, the CLI's progress bar inside the core linter (core → cli).
- **Conditions:**
  - **C:** all `AGENTS.md` files removed;
  - **A:** sqlfluff's real `AGENTS.md` files (7,757 words, mentioning the core and api contracts, the layer order and the dialect rule);
  - **B:** the deny-list UCN model plus the validator, with `AGENTS.md` removed.
- **Agents:** Claude Haiku. A and B twice per task, C once: 20 runs on the 269-file package.
- **Grading:** against the pristine model; only *new* violations count. The pre-existing dialect conflict is recorded as known.

| Condition | Runs with a new architecture violation | Avg tokens | Avg time | Avg tool calls |
|---|---|---|---|---|
| C: no agent docs | **2/4** (T2, T3) | 66.5k | 84 s | 16.0 |
| A: real AGENTS.md | **1/8** (T2) | 82.0k | 122 s | 21.8 |
| B: UCN + validator | **0/8** | 70.2k | 122 s | 18.4 |

**What happened:**
- **T2 discriminated.** C and one A run imported `BaseSegment` from the parser into `core/helpers/string.py`; A did it under `TYPE_CHECKING` "to avoid a circular import". import-linter counts such imports too, so sqlfluff's CI would have failed. Both B runs used a structural `Protocol` and cited the layer rule. The validator reported each violation with its transitive chains (helpers → parser → … → errors, types).
- **T3:** C imported `sqlfluff.cli.formatters` into `api/simple.py` (forbidden, and it creates an `Api ↔ Cli` cycle). All four A runs and all four B runs moved the formatting into `core/formatter.py` and made the CLI delegate to it: a larger change, but one that conforms.
- **T1 and T4 didn't discriminate.** Everyone used `core.dialects.dialect_selector` and the plugin manager in T1. In T4 the progress bar already existed; most agents added tests, and B agents explained that reusing CLI helpers would break `Core forbids Cli`.
- **No tampering:** no B agent edited the model, and no A agent edited the docs.
- **Cost:** B used **14% fewer tokens than A**. The 80-line model is cheaper to read than 7.7k words of prose. Both were slower than C.

**How strong is this?**
- B 0/8 vs C 2/4: one-sided Fisher exact p = 0.09. B 0/8 vs A 1/8: p = 0.5. **Directionally consistent, not significant.**
- **The comparison isn't "UCN vs the lightweight stack".** sqlfluff's real stack also runs import-linter in CI, and an agent with import-linter in its loop would probably also reach 0/8. That arm couldn't be run here.
- **What it does show:** a *checked* rule in the agent's loop prevented a violation that the same rule in *prose* didn't (T2-A2). The checked model also cost fewer tokens than the prose.

## 7.7 Updated conclusion

| Question | Evidence so far |
|---|---|
| Does UCN find real problems? | **Yes:** a prose rule contradicted by 12 modules (sqlfluff); circular, undeclared runtime dependencies between published packages (excalidraw). |

## 7.8 Third-party checkers in containers (v0.5.1)

The comparisons that needed third-party code were run with **import-linter 2.15** and **dependency-cruiser 16.10.4**, each in a Docker container with the repository mounted read-only ([trials/containers/](../trials/containers/)).

### import-linter on sqlfluff

| Run | Result |
|---|---|
| sqlfluff's own contracts at `1682e11` | 4 kept, 0 broken, 4 ignored imports (ground truth confirmed) |
| Generated from the **allow-list** model | 24 kept, 0 broken (the validator: 0 violations) |
| Generated from the **deny-list** model | 10 kept, **2 broken**: `rules` → `dialects` (10 modules) and `utils` → `dialects` (2 modules), exactly the 12 modules the validator reports |
| sqlfluff's own contracts on the 20 agent workspaces of experiment v2 | broken in exactly **T2-A2, T2-C1, T3-C1**, the same 3 runs the validator flagged; kept in the other 17 |

**Running the real tool found five exporter and semantics bugs that reading the output never would have:**

| Bug | Fix |
|---|---|
| `ignore_imports` named packages (`sqlfluff.core.plugin -> sqlfluff.core.rules`); import-linter requires exact module pairs and rejects entries that match nothing | ignores are derived from the observed file-level imports each deviation covers |
| Convention contracts checked **indirect** imports (import-linter's default), so `api → linter → templaters → jinja2` counted as `api` importing jinja2 | `allow_indirect_imports = True`, matching the validator's direct check |
| A waiver to `Linter` also covered imports of files owned directly by its container `Core` | the reverse match is limited to `data` held by a store |
| `independent` was direct-only; import-linter's independence contract is transitive (it broke in T2 through `helpers.string → parser → … → helpers.slice`) | `independent` is now transitive on the file graph, like `layers` |
| (dependency-cruiser) see below | |

After the fixes, the generated deny-list layers contract has 5 ignores against sqlfluff's 4. The extra one, `plugin.lib → rules`, is a real import covered by the same component-level deviation: UCN waivers are scoped to element pairs, sqlfluff's ignores to single modules. That's a granularity difference (review C2), not a disagreement.

### dependency-cruiser on excalidraw and Shortly

| Run | Result |
|---|---|
| excalidraw, generated config, tsconfig aliases | 1,150 modules, 4,969 dependencies, 246 file-level violations → **22 element pairs, identical to the validator's 22** |
| excalidraw, validator reading dependency-cruiser's JSON (`--deps`) | the same 22 pairs as its own scan |
| Shortly, generated config | `guard → links` and `web/app → web/client` (not-in-allowed); the validator reports the same 2, classified as VIOLATION and MODEL-UPDATE, plus the 2 dependencies covered by waivers (allowed in the generated config) |

**Bugs found by running it:**
- dependency-cruiser rejected `(?:/.*)?` as an **unsafe regex** (a quantifier inside a quantified group). The dependency-cruiser export now uses its own glob conversion without nested quantifiers.
- `type-only` was in the list of external dependency types, which allowed *every* type-only import, internal ones included. That hid `common → element/types` and `examples → element/types`.
- Bare directory names inside braces (`{examples,scripts}/**`) produced `examples//…`.

### Agent arm A′: sqlfluff's full lightweight stack

Arm A′ is the real `AGENTS.md` **plus import-linter feedback in the loop**: the agent ran the containerized `lint-imports` before finishing and had to fix every BROKEN contract. It covers the same 4 tasks, 2 runs each, with Claude Haiku. That's 8 runs, graded with both import-linter and the validator.

| Condition | Runs with a new violation | Avg tokens | Avg time | Avg tool calls |
|---|---|---|---|---|
| C: no agent docs | 2/4 | 66.5k | 84 s | 16.0 |
| A: AGENTS.md | 1/8 | 82.0k | 122 s | 21.8 |
| **A′: AGENTS.md + import-linter in the loop** | **0/8** | 79.6k | 120 s | 21.4 |
| **B: UCN model + validator** | **0/8** | 70.2k | 122 s | 18.4 |

**Reading:**
- **The check in the loop is what prevents violations, not UCN as such.** The full lightweight stack (A′) reached the same 0/8 as UCN (B). In T2 and T3, A′ agents produced the same conforming designs as B: a structural `Protocol` in the helpers, formatting moved into `core.formatter`.
- **UCN's measurable differences in this experiment:** about **12% fewer tokens** than A′ (an 80-line model vs 7.7k words of prose), and rules import-linter doesn't have here (the dialect rule, two library conventions, governance with expiry). No difference in violations or time.
- n is small (8 runs per arm). The result agrees with the reviewers' prediction that the lightweight stack with a checker in the loop is a strong baseline.

### What the container runs settle

1. **The validator agrees with both mature tools on real code**, once the five bugs above were fixed: same contracts kept and broken on sqlfluff, the same 3 out of 20 agent runs flagged, and identical element pairs on excalidraw.
2. **Exporting to existing checkers works.** The generated configs run, pass or fail as the model predicts, and import-linter accepts the exact ignores.
3. **On preventing violations, UCN is as good as the lightweight stack, not better.** Its edge is cost and coverage: fewer tokens, prose-only rules made checkable, expiring waivers, authority modes and adoption gates. Whether that edge is worth a second model file is what the pilot must decide. Being able to *generate* the import-linter and dependency-cruiser configs from the model, instead of maintaining both, reduces that cost.
